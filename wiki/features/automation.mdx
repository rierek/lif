**Built for scripts and coding agents.** Most commands print JSON, GraphQL runs from the command line, and `lif prime` teaches a coding agent how to use Lif. No server is needed: scripts and agents work on the files.

## How it looks

A pipeline with `jq`. `--quiet` prints IDs only, `--full` adds the body to the JSON:

```bash
lif list --json | jq -c '.[] | {id, title, status}'
lif list --json --full | jq -r '.[] | select(.body) | .body'
lif list --quiet
```

A GraphQL one-liner (real output):

```text
$ lif graphql '{ items { id title status } }'
{
  "items": [
    {
      "id": "ft-2gae",
      "title": "Ship v1",
      "status": "todo"
    }
  ]
}
```

Other options: variables with `-v`, a query on stdin, `--schema`. See [`lif graphql`](../../reference/commands/lif-graphql/).

**With `lif prime`, `--json` and GraphQL, a script or coding agent works on your backlog without a server.**

## What you get

<KeyValueList>
  <KeyValueItem term="JSON from the shell">Many commands take `--json`, for example `list`, `next`, `create`, `complete`, `progress`, `roadmap`, `check`. Errors carry codes such as `NOT_FOUND` or `VALIDATION_ERROR`. Exit code: 0 on success, 1 on error; `lif run` returns the exit code of the failing step.</KeyValueItem>
  <KeyValueItem term="GraphQL without a server">`lif graphql '<query>'` (alias `lif query`) also reads stdin. A mutation through the CLI works the same way, for example `createItem` with `title` and `type`.</KeyValueItem>
  <KeyValueItem term="Agents that learn Lif from Lif">`lif prime` prints a prompt that teaches a coding agent how to use Lif, and it runs without a loaded store. Agents learn from `lif prime` and `--help`, not from prior knowledge.</KeyValueItem>
  <KeyValueItem term="Review findings become items">`lif promote <artifact> <finding-id>...` creates items from the findings of a review artifact. It writes nothing if a chosen finding is malformed and skips findings that were already taken over.</KeyValueItem>
</KeyValueList>

## Write recipes

```sh
lif update <id> --body-append "Found the cause."
lif update <id> --body-replace-old "TODO" --body-replace-new "DONE"   # each flag requires the other
lif tag <id> [id...] --tag backend --remove-tag draft
ETAG=$(lif show <id> --etag-only)
lif update <id> --if-match "$ETAG" --status in-progress              # fails if the item changed
```

`--tag` and `--remove-tag` merge into the existing tags.

## Tasks

A task is a named list of shell steps. `lif run` lists the tasks, and `lif run <task> [args...]` runs one. A person and an agent run the same steps the same way.

A project task in `.lif.yml`. `args: [id]` makes `$id` a required argument:

```yaml
tasks:
  po-accept:
    desc: Accept an item as PO and commit the item file
    args: [id]
    steps:
      - |
        "$LIF" update "$id" --tag accepted --body-append "## PO acceptance $(date +%F)"
        file="$("$LIF" path)/$("$LIF" show "$id" --json | jq -r .path)"
        git add -- "$file"
        git commit -m "chore($id): PO acceptance" -- "$file"
```

```sh
lif run po-accept lif-ab12
```

A global task in `~/.lif/tasks.yml`, available in every project. The step passes all arguments on with `"$@"`:

```yaml
tasks:
  wt:
    desc: Work with worktrees
    steps: ['just -g wt "$@"']
```

```sh
lif run wt start lif-ab12 milestone/0.16   # runs: just -g wt start lif-ab12 milestone/0.16
```

Steps get `LIF`, `LIF_ROOT`, `LIF_TASK` and `LIF_TASK_ORIGIN` in the environment. A failing step stops the run and sets the exit code of `lif run`. See [Tasks](../../reference/configuration/#tasks) in the configuration reference for the schema, the rules and the trust note.

## Hooks

A hook runs a task by itself when an item is created or one of its fields changes: `status`, `type`, `parent`, `tags` or any extra front matter key of your workflow. Tasks are the *what*, hooks are the *when*. Nobody has to remember the step, neither a person nor an agent. A hook reacts after the change is written. A gate checks before the write and can refuse the change.

Project hooks run only after you have read them and run `lif hooks allow`. `lif hooks` lists every hook and gate and says whether the project hooks run.

### Open and close a container worktree

Two hooks do what a `just` recipe did by hand. `todo -> in-progress` opens the worktree of the item, and `-> completed` closes it:

```yaml
tasks:
  wt-open:
    desc: Create the container worktree for an item
    args: [id, line]
    steps:
      - |
        [ -n "$line" ] || { echo "item $id has no 'line' field" >&2; exit 1; }
        common="$(git rev-parse --path-format=absolute --git-common-dir)"
        [ -d "$(dirname "$common")/../worktrees/$id" ] && exit 0
        just -g wt start "$id" "$line"
  wt-close:
    desc: Remove the container worktree after acceptance
    args: [id]
    steps:
      - |
        common="$(git rev-parse --path-format=absolute --git-common-dir)"
        [ -d "$(dirname "$common")/../worktrees/$id" ] || exit 0
        just -g wt finish "$id"
hooks:
  open-worktree:
    event: [created, updated]
    changed: [status]
    to: [in-progress]
    type: [feature, task, bug]
    run: wt-open
    args: [id, line]
  close-worktree:
    event: [updated]
    changed: [status]
    to: [completed]
    run: wt-close
    args: [id]
```

- **Safe to fire twice.** Each task checks its own precondition and exits 0 when there is nothing to do: `wt-open` does nothing when the worktree exists, `wt-close` does nothing when it does not.
- **Two path rules.** `git rev-parse --git-common-dir` gives the same hull from the main checkout and from every container worktree, so the task does not depend on where Lif runs. The integration line comes from the item field `line`, because the current branch of a container worktree is the container branch, not the line. Set it with `lif update lif-ab12 --set line=milestone/0.16`. `line` is an extra key: Lif passes it as the argument `line` without any declaration.
- **Complete from the integration checkout.** `just -g wt finish` refuses to remove the worktree that it runs in. If you complete an item from inside `worktrees/<id>/`, `wt-close` fails with a warning. The item is still completed.

### Gates

A gate has `stage: before`. It runs before the write, and a non-zero exit refuses the change: nothing is written. This gate refuses `completed` until the item is listed in the file that its field `target_entry` names:

```yaml
tasks:
  check-target-entry:
    args: [id, target_entry]
    steps:
      - |
        [ -n "$target_entry" ] || { echo "field target_entry is empty" >&2; exit 1; }
        grep -qF -- "$id" "$target_entry" || { echo "$id not found in $target_entry" >&2; exit 1; }
hooks:
  require-target-entry:
    stage: before
    event: [updated]
    changed: [status]
    to: [completed]
    run: check-target-entry
    args: [id, target_entry]
    message: "Entry missing in the target file. Add it, then complete the item."
```

```sh
lif complete lif-ab12 --set target_entry=docs/RELEASE.md
```

If `docs/RELEASE.md` does not list `lif-ab12`, the command exits with code 1, writes nothing and prints the fixed `message` first and the output of the task below it:

```text
Error: hook "require-target-entry" blocked the change of lif-ab12: Entry missing in the target file. Add it, then complete the item.
lif-ab12 not found in docs/RELEASE.md
```

With `--json`, the same text is the `error` and the `code` is `POLICY_VIOLATION`.

- A gate fails closed. A gate that cannot run, for example an unknown task, blocks the change with `could not run: <error>`.
- A gate in a project config that is not allowed does not run. Lif warns and counts the gates: `hooks in <path> are not allowed (1 gates not enforced)`.
- `LIF_NO_HOOKS` with any non-empty value skips after hooks and gates. It is a deliberate bypass, and every process that a hook starts inherits it. An agent must fix what the gate reports and must not set it.

### Limits

- A hook sees only changes that go through Lif. Delete, `lif check --fix`, `lif rename`, `lif order`, hand edits of item files and git merges fire nothing.
- A task that wants to write an item can run `"$LIF" update ...`: such a call fires no hooks, so hooks do not chain.
- The CLI can show a stale item after a hook wrote it. Read it again with `lif show --json`.

See [Hooks](../../reference/configuration/#hooks) in the configuration reference for every key, the item fields, the trust rules and all limits.

## Errors

Without `--json`, an error goes to stderr as `Error: <message>` plus `Run '<command> --help' for usage.`, and stdout stays empty. With `--json`, the error is a JSON object on stdout and stderr stays empty. Errors before JSON handling, such as an unreadable config or a missing store, still go to stderr. `lif run` is the exception: it prints only `Error: task "<name>": step <n> of <total> failed (exit code <c>)` and exits with the exit code of the failing step. A change that a gate blocks prints no usage line either: see [Gates](#gates).

## Tips

<Aside type="tip" title="How do I set up agent hooks?">

A session hook runs `lif prime` at session start and before context compaction. The agent then starts each session with the Lif instructions. The Lif repository does this for Claude Code with `SessionStart` and `PreCompact` hooks:

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{ "type": "command", "command": "lif prime" }] }],
    "PreCompact":   [{ "hooks": [{ "type": "command", "command": "lif prime" }] }]
  }
}
```

This snippet is the hook file shipped in `extras/claude/plugins/lif-prime/hooks/hooks.json` in the Lif repository. It applies to Claude Code. Other agents need their own hook mechanism, or you paste the `lif prime` output once. [Agent onboarding](../../overview/agent-onboarding/) covers hooks and drift prevention.

Convention, not enforced by Lif: put the item ID in the commit message so agent work stays traceable.

</Aside>

<Aside type="tip" title="How do I validate after automated changes?">

Run `lif check` after every automated change.

- Exit 1 means at least one problem. Exit 0 means none.
- `--strict` counts policy warnings (missing required fields, unknown commit SHAs) as problems.
- `--fix` removes broken links and self-references. Cycles, configuration errors, attachment orphans and policy warnings remain.
- `--json` returns `success`, `config_errors`, `item_issues` (`broken_links`, `self_links`, `cycles`) and more.
- For what `lif check` does and does not cover, see [Flexible planning](../project-planning/#limits).

</Aside>

## Details

- `lif graph` uses `--format json`. In JSON mode the human-readable lines are omitted.
- With a server, `lif-serve` offers `/api/graphql` and a playground at `/playground`.
- `lif promote` takes a review artifact that follows the findings schema. It validates every selected record and the `--parent` item first, writes nothing if one fails, and then creates one item per record with the configured default status. The command page describes the artifact format. See [`lif promote`](../../reference/commands/lif-promote/).
- GraphQL `createItem` without `status` sets the configured default status (0.14).
- `lif check` returns 1 on at least one problem. Normal errors do not use exit code 2, except `lif run`, which returns the exit code of the failing step.
- On a GraphQL error the CLI prints `Error:` and a message. It returns no partial data.

## Limits

- Parse `--json` against the [JSON schema files](../../reference/json-output/#json-schemas). `lif graphql` and the findings artifact of `lif promote` have none.
- Use the Web server for subscriptions and for the agent, terminal and worktree parts of the schema. They fail in the CLI with messages such as "agent manager not available", and subscriptions run only over the WebSocket of `lif-serve`.
- Run `lif check` after files you write directly. They bypass the write rules.
