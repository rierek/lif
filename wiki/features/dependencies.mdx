**Know what you can start now.** Items can block each other. Lif works out what is blocked and what is ready, and `lif next` answers "What now?" for people and for agents without their own planning logic.

## How it looks

<DepChain />

Task `ft-o87g` ("Reset page") waits for `ft-957g` ("Send reset mail"):

```text
$ lif update ft-o87g --blocked-by ft-957g
Updated ft-o87g ft-o87g--reset-page.md
$ lif list --is-blocked -q
ft-o87g
$ lif list --ready -q
ft-957g
```

`lif graph --format mermaid --relation blocks` draws the edge (node styling left out):

```text
ft-957g -->|blocks| ft-o87g
```

A cycle is refused when you add the link:

```text
$ lif update ft-957g --blocked-by ft-o87g
Error: adding blocked-by relationship would create cycle: [ft-957g ft-o87g ft-957g]
```

After you complete the blocker with `lif complete ft-957g`, `ft-o87g` is ready:

```text
$ lif list --ready -q
ft-o87g
```

The ready list holds leaf work only. In this store the feature `ft-igeu`, the epic `ft-txrv` and the milestone `ft-2gae` are containers, so neither `lif list --ready` nor `lif next` returns them.

<WhyItMatters>
**Blocked work stays out of the ready list, so you and your agents start with what is unblocked.**
</WhyItMatters>

## Details

- `blocking` lists the items this item blocks. `blocked_by` lists the items that block this one. Lif stores an edge on one side only: on the item you just changed. On read, Lif merges both directions. Deleting an item removes all references to it.
- An item is **blocked** if a direct blocker is still active, or if an ancestor in the parent chain is blocked.
- An item is **ready** if it is not blocked, its status is not `in-progress`, `draft` or an archive status, no ancestor is `completed` or `scrapped`, and its type is not a container type. Container types are the types on rank 1 to 3: `milestone`, `epic` and `feature` by default, and any custom type you put on those ranks. `lif next` and `lif list --ready` therefore return leaf work only.
- Filters: `lif list --ready`, `--is-blocked`, `--unblocked`. `--ready` and `--is-blocked` exclude each other.
- `lif graph` takes `--depth` and `--relation parent|blocks`.
- Lif refuses a link that would leave items waiting for each other for ever, and `lif check` reports one that a manual edit made. That is a cycle of blocking links in any mix of `blocking` and `blocked_by`, a blocker below the item it blocks (a blocked parent blocks its children), and a blocker above it (a child counts as done once its parent is done), alone or chained. The refusal names the items, for example `adding blocked-by relationship would create cycle: [ft-p ft-d ft-p] (a child is blocked while its parent is blocked and counts as done once its parent is done)`. `lif update` with several IDs checks every item before it writes the first one.
- The cycle rules look at the links and the parent chain, never at the status. A link that would deadlock is refused when the blocker is already `completed` or `scrapped`, and `lif check` reports a finished structure too, because reopening one item would bring the deadlock back. Remove such a link with `--remove-blocked-by` or `--remove-blocking`.
- `lif check` prints a cycle as an arrow path that starts at its smallest ID and closes on it, with its link type: `blocking`, `parent` or `blocking+parent`. A cycle path reads in the direction of the links; a loop of parent links reads from child to parent. `lif check --fix` removes broken links and self-references, never cycles.

## Limits

- Keep both sides of an edge in step if you edit by hand. There is no symmetry check: `A.blocking=[B]` and `B.blocked_by=[A]` can both be present, or only one side, and `lif check` does not report a mismatch.
- Mark a blocker `completed` or `scrapped` to release the items it blocks. "Done" is fixed in the code. `draft`, `todo`, `in-progress` and custom archive status keep blocking. This is the one place where status counts: the cycle rules above ignore it.
- Order ready items yourself, or use `lif roadmap`. `lif next` ignores dependency order among ready items. A blocker that does not exist in the store is ignored, and a blocker blocks by its own status only, not by its parents.
