**A vague requirement becomes verifiable when each criterion has one trigger, one behavior and a value you can measure.** We write criteria in the EARS notation inside the item body, and a small validator checks the form on every item.

## A vague requirement

An item arrives with this body. Every line sounds reasonable. None of it can be checked:

```text
Users say the report export is "too slow and sometimes broken".

## Acceptance Criteria

1. The export should be fast.
2. It must work for large reports.
3. The user can see when something goes wrong.
```

The item lives in a throwaway store, created with `lif create "Report export" -t feature --body-file body.md`. Run the validator on the item file (how to get it: see [Run the validator](#run-the-validator)):

```bash
node ears-validator.js .lif/app-bfs9--report-export.md
```

Excerpt of the real output (the validator prints a fix guide after this):

```text
EARS Validation FAILED

**File:** .lif/app-bfs9--report-export.md
**Valid Statements:** 0
**Invalid Statements:** 3

### Line 14

**Statement:** `The export should be fast.`

**Error:** Invalid modal verb "should" - use "SHALL" instead

**Suggestion:** The export SHALL be fast.
```

Lines 15 and 16 fail the same way, for `must` and `can`.

<Aside type="caution" title="The suggestion is not the fix">
"The export SHALL be fast" passes the form check, but nobody can test it. The validator checks the sentence shape. It cannot know what "fast" means. You do the rewrite.
</Aside>

## The same requirement in EARS

Ask for each line: what triggers it, what exactly happens, what number or name would tell us it happened. The result:

```text
## Acceptance Criteria

1. WHEN a user requests a CSV export of a report with up to 100000 rows THE System SHALL deliver the file within 10 seconds
2. WHEN a user requests an export of a report with more than 100000 rows THE System SHALL start a background job and show its status
3. IF the export fails THEN THE System SHALL show an error message that names the failed report
4. WHILE an export job runs THE System SHALL display the number of rows written
5. THE System SHALL write every export file as UTF-8 with a header row
```

One `lif update app-bfs9 --body-file body.md` stores it. The validator now says:

```text
EARS Validation PASSED

**File:** .lif/app-bfs9--report-export.md
**Valid Statements:** 5
**Status:** All acceptance criteria follow valid EARS patterns.
```

`lif check` also passes: it checks the store, not the criteria.

## The idea

EARS (Easy Approach to Requirements Syntax) was created by Alistair Mavin and colleagues; [his EARS page](https://alistairmavin.com/ears/) is the primary source (link checked 2026-10-14, a third-party site, not part of Lif). EARS gives a criterion one of a few fixed shapes. The keyword `SHALL` is the only modal verb, and keywords are uppercase:

| Pattern | Shape |
|---|---|
| Always true | `THE System SHALL …` |
| Event | `WHEN <event> THE System SHALL …` |
| State | `WHILE <state> THE System SHALL …` |
| Optional feature | `WHERE <feature> THE System SHALL …` |
| Unwanted behavior | `IF <condition> THEN THE System SHALL …` |
| Complex | `WHILE <state> WHEN <event> THE System SHALL …` |

The patterns are the six listed in `ears-notation.md`, which ships with the validator. The shape forces the two questions that vague text skips: when, and what exactly. A numbered list inside the item makes each criterion addressable, so a review can say "criterion 2 is not covered" (see [Plan, implement, check with Lif](../plan-implement-check/)).

An item is a Markdown file, so the criteria are plain text in its body. Lif does not parse them. The format is described in the [item file format](../../reference/item-file-format/).

## Run the validator

<Aside type="note" title="Own tool, not part of Lif">
The validator is a separate script from the same author. Lif does not include it, call it or know about it. It needs Node.js and uses only `fs` and `path`.
</Aside>

It is published as a [public Gist](https://gist.github.com/xRiErOS/5abdbeaa3aadc0f831b5ef426f4787db) with two files: `ears-validator.js` and `ears-notation.md`. Link checked 2026-10-14. Download the script and run it on any Markdown file:

```bash
node ears-validator.js path/to/item.md
```

The script reads the numbered list under a heading called `Acceptance Criteria` (levels 1 to 4; the German `Akzeptanzkriterien` also works). It exits with 0 when all criteria pass and with 1 otherwise, so it fits a hook or a CI step.

## Limits and open points

- The validator checks form only. A criterion like `THE System SHALL be fast` passes the shape check (the validator proposes it itself above). Choosing measurable values is human work.
- Verification beyond the form is yours: a test, a manual check or a review per criterion.
- Writing criteria this way is a practice, convention, not enforced by Lif. Lif accepts any body text.
- The validator ran here on a plain item file with one criteria section. We did not test other layouts.
