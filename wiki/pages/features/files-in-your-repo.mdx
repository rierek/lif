**Your backlog is a folder of files. Everything that reads files already speaks Lif.** You, your editor, Git and your coding agent need no plugin and no server. There is no database and no export step.

## How it looks

An item is one Markdown file with YAML front matter. Here is the item on disk, and the same item printed by `lif show`:

<div class="pair not-content">
  <TerminalWindow title={`.lif/${demo.file.name}`} html={demo.file.html} cols={64} />
  <TerminalWindow title="~/app" command={demo.show.command} html={demo.show.html} cols={64} />
</div>

The `.lif/` directory lives inside your repository, so Git versions the backlog with the code. `lif complete --commit HEAD --summary "Mail sent"` changed this item. Excerpt of the real `git diff` (context lines left out):

```diff
-status: todo
+status: completed
+priority: normal
-updated_at: 2026-10-14T19:17:18Z
+updated_at: 2026-10-14T19:17:23Z
+commit: 22b4b97e63ce8e8bdf836c6aa509adfeb1cca41b
+## Summary of Changes
+
+Mail sent
```

- `status` and `updated_at` are known fields. Lif rewrites them in place.
- `commit` is an extra key. Lif writes it after the known fields. It holds the commit SHA.
- The body gains a `## Summary of Changes` section.

With `lif.anchor: repo-root`, two worktrees read the same store:

<Aside type="tip" title="Why it matters">
Your backlog outlives any tool: if you stop using Lif, your items stay readable Markdown files. Backlog changes get the same review as code, because they appear in the diff of the branch that makes them.
</Aside>

<details>
<summary>How to use Lif with Git</summary>

Treat items like code: commit, review, merge.

- Put the item ID in the commit title and use one branch per container item (epic or feature). This is a convention, not enforced by Lif.
- Set `lif.anchor: repo-root` so all worktrees see the same store.
- On a merge conflict in an item file, resolve the front matter or body by hand like any text file, then run `lif check`. Lif adds no merge tooling.
- A parse error aborts loading (`loading <path>: ...`), so fix conflict markers before you run any `lif` command.

</details>

<details>
<summary>Example: pre-commit hook</summary>

Lif ships no hook, no installer and no recipe. This is an example, not product code. A Git `pre-commit` hook that calls `lif check`:

```bash
#!/bin/sh
# .git/hooks/pre-commit
lif check || exit 1
```

`lif check` exits 1 on at least one problem, and Git then aborts the commit. Use `lif check --strict` to let warnings stop the commit too. `lif check` resolves the store from the current directory, and Git runs the hook from the repository root.

</details>

<details>
<summary>How to use attachments</summary>

An item can have a directory `attachments/<item-id>/` for a design note or a screenshot.

- On load, Lif skips the `attachments/` directory. It never looks for items there.
- `lif check` reports a directory without a matching item as a problem (`attachments/<id> has no item <id>`, exit 1). An item in the archive counts as present.
- Lif does not create the directory for you. Create it yourself and mention the file in the item body. This is a convention, not enforced by Lif.

</details>

<details>
<summary>How to link items from a README</summary>

Keep the README as the entry point and let the items hold the work state. Do not copy status into the README. Generate a roadmap instead:

```bash
lif roadmap --format markdown
```

Real output (excerpt):

```markdown
# Roadmap

## Milestone: Ship v1 ([ft-2gae](.lif/ft-2gae--ship-v1.md))

### Epic: Login flow ([ft-txrv](.lif/ft-txrv--login-flow.md))
```

Useful options: `--no-links`, `--link-prefix`, `--depth`, `--tags`, `--include-done`. See [`lif roadmap`](../../reference/commands/lif-roadmap/).

</details>

<details>
<summary>File format and store layout</summary>

- Layout: `---`, YAML front matter, `---`, then the Markdown body.
- File name: `<id>--<slug>.md`. ID and slug are not front matter fields. Lif derives them from the file name.
- Field order: `title`, `status`, `type`, `priority`, `tags`, `created_at`, `updated_at`, `order`, `parent`, `blocking`, `blocked_by`. The first front matter line is a YAML comment `# <id>`.
- Unknown keys stay. Lif writes them in alphabetical order after the known fields.
- The store is the directory `.lif/` next to the configuration `.lif.yml`. New items go into the root of the store. The archive goes into `archive/`.
- Manual order uses the field `order` (a fractional index). `lif order` writes only the item you place.
- Without `lif.anchor: repo-root`, each worktree uses its own store.
- `worktree.*` settings (`base_ref`, `path`, `setup`, `run`, `integrate`, `fetch_timeout`) configure worktrees. See [Configuration](../../reference/configuration/).
- `lif.commit_field` (default `commit`) holds the Git SHA. `lif check` warns if the SHA is not in the repository. Outside a Git repository the check is skipped. Lif refuses to resolve `HEAD` outside a repository, and reports `"HEAD" does not resolve to a commit`.
- A **Liff** is the Markdown file of an item. See the [glossary](../../reference/glossary/).

</details>

## Limits

- Edit by hand, then run `lif check`. Lif does not check manual edits on load. See [Flexible planning](../project-planning/#limits) for what `lif check` covers.
- Write within the limits that apply when you write through Lif: body at most 1 MiB, title at most 1000 characters, tags in lower case, starting with a letter, hyphens only between characters.
- Fix or remove a broken `.md` file before you run other commands. One unparsable file aborts the whole load (`loading <path>: ...`) and Lif then returns no items.
- Keep file names equal to IDs and IDs unique. `lif check` reports neither a differing file name nor a duplicate ID. With a duplicate ID, the file loaded later silently overwrites the other.
- Test Obsidian Bases yourself before you rely on it. Compatibility is unclear: nothing in the code or the docs says anything about it. See [Surface independence](../surface-independence/#editors-such-as-obsidian).
- Add the hook yourself. Lif ships none, and CI does not run `lif check` either.
- Set `lif.anchor: repo-root` if worktrees should share items. Without it, changes come together only through a merge.
- Run `lif check` after a merge, and read the result with care. A merge can combine edits into a state `lif check` does not catch, for example mixed-field cycles [et2a]. See [Known limitations](../../known-limitations/).
- Stop `lif-serve` and remove active worktrees before `lif rename --prefix`. It refuses while they exist.
