**Your backlog travels with your code.** The `.lif/` directory lives inside your repository. Items are files, so Git versions, diffs and merges them with the code. You need no separate ticket system.

## How it looks

A status change touches only front matter lines. This is `lif start` on one item, shown with `git diff` (context lines left out):

```diff
-status: todo
+status: in-progress
+priority: normal
-updated_at: 2026-10-14T19:17:18Z
+updated_at: 2026-10-14T19:17:23Z
```

`lif complete --commit HEAD` stores the commit SHA in the item (`commit: 22b4b97e...`).

With `lif.anchor: repo-root`, two worktrees read the same store:

```text
repo/                  main worktree, holds .lif/ and .lif.yml
worktrees/feature-x/   second worktree, reads repo/.lif/
```

<details>
<summary>How to use Lif with Git</summary>

Treat items like code: commit, review, merge.

- Put the item ID in the commit title and use one branch per container item (epic or feature). This is a convention, not enforced by Lif.
- Set `lif.anchor: repo-root` so all worktrees see the same store.
- On a merge conflict in an item file, resolve the front matter or body by hand like any text file, then run `lif check`. Lif adds no merge tooling.
- The fixed field order and alphabetical extra keys keep diffs small. A parse error aborts loading (`loading <path>: ...`), so fix conflict markers before you run any `lif` command.

</details>

<details>
<summary>Example: pre-commit hook</summary>

Lif ships no hook, no installer and no recipe. This is an example, not product code. A Git `pre-commit` hook that calls `lif check`:

```bash
#!/bin/sh
# .git/hooks/pre-commit
lif check || exit 1
```

`lif check` exits 1 on at least one problem, and Git then aborts the commit. Use `lif check --strict` to let warnings stop the commit too. `lif check` resolves the store from the current directory, and Git runs the hook from the repository root.

</details>

## Details

- The store is the directory `.lif/` next to the configuration `.lif.yml`. New items go into the root of the store. The archive goes into `archive/`.
- Fields are in fixed order. Extra keys are in alphabetical order.
- Manual order uses the field `order` (a fractional index). `lif order` writes only the item you place.
- Without `lif.anchor: repo-root`, each worktree uses its own store.
- `worktree.*` settings (`base_ref`, `path`, `setup`, `run`, `integrate`, `fetch_timeout`) configure worktrees. See [Configuration](../../reference/configuration/).
- `lif.commit_field` (default `commit`) holds the Git SHA. `lif check` warns if the SHA is not in the repository. Outside a Git repository the check is skipped. Lif refuses to resolve `HEAD` outside a repository, and reports `"HEAD" does not resolve to a commit`.

## Limits

- Add the hook yourself. Lif ships none, and CI does not run `lif check` either.
- Set `lif.anchor: repo-root` if worktrees should share items. Without it, changes come together only through a merge.
- Run `lif check` after a merge, and read the result with care. A merge can combine edits into a state `lif check` does not catch, for example mixed-field cycles [et2a]. See [Known limitations](../../known-limitations/).
- Stop `lif-serve` and remove active worktrees before `lif rename --prefix`. It refuses while they exist.
- Keep IDs unique. With a duplicate ID the file loaded later wins, without a message. See [Flexible planning](../project-planning/#limits) for the gaps of `lif check`.

<Aside type="tip" title="Why it matters">
Backlog changes get the same review as code: they appear in the diff of the branch that makes them.
</Aside>
